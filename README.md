# Лабораторные работы

Решение на C# / .NET 10. Примеры из каталога `medj` изучены и адаптированы
в проекте `medjLab`; исходные примеры сохранены.

Отдельного текста условий в исходниках нет. Порядок работ восстановлен по
примерам: стиль кода, затем S, O, L, I, D. Это предположение следует сверить
с методичкой, когда она появится.

| Работа | Тема из instruction.md | Содержание | Исходный пример |
|---|---|---|---|
| 1 | 3 — Красота и здоровье | Стиль кода: расписание процедур | bad1 / good1 |
| 2 | 16 — Роботы | SRP: отчёт об обслуживании робота | S |
| 3 | 13 — Транспорт | OCP: отправка транспорта | O |
| 4 | 11 — География и метеорология | LSP: текущий и архивный журналы наблюдений | L |
| 5 | 8 — Мифы и сказки | ISP: способности сказочных существ | I |
| 6 | 11 — География и метеорология | DIP: метеостанция и сменные датчики | D |

## Запуск

Из корня решения:

```powershell
dotnet build medjLab.sln
dotnet run --project medjLab -- all
dotnet run --project medjLab -- 3 good
dotnet run --project medjLab -- 4 bad
```

Без аргументов выводится справка. Первый аргумент — номер 1–6 или `all`.
Второй — `bad`, `good` или `both` (по умолчанию). Каждая работа хранится
в `medjLab/Labs/LabNN`: `Bad.cs`, `Good.cs`, `Demo.cs`.
Работа 2 записывает два отчёта в `reports` относительно текущего каталога;
повторный запуск заменяет эти учебные отчёты.

## Что объяснять при защите

1. **Стиль кода.** В Bad — неясные имена, открытые поля, приведения object
   и повторяющееся вычисление среднего. В Good — осмысленные имена,
   свойства, общий интерфейс, расписание и отдельный расчёт статистики.
   Средняя длительность до добавления процедуры — 25 минут, после — 30.
2. **SRP.** Bad объединяет модель, расчёт и вывод. В Good данные робота,
   калькулятор, консольный и файловый вывод имеют отдельные ответственности.
   Коэффициент 1,2 — условная надбавка за обслуживание; результат для 1000 — 1200.
3. **OCP.** Bad распознаёт транспорт цепочкой условий и не знает мотоцикл.
   Good работает с ITransport. Добавление Motorcycle не меняет Dispatcher.
4. **LSP.** Архивный журнал Bad наследуется от изменяемого журнала,
   но запрещает Add. Ожидаемое исключение перехвачено в демонстрации.
   В Good оба журнала подставляются в общий клиент чтения Print;
   запись доступна лишь через контракт IWritableWeatherJournal.
5. **ISP.** Общий интерфейс Bad заставляет русалку реализовывать полёт.
   Good разделяет полёт, плавание и колдовство: каждый класс реализует
   только свои способности. Баба-яга объединяет два подходящих интерфейса.
6. **DIP.** Bad создаёт GroundThermometer внутри станции. В Good станция
   зависит от ITemperatureSensor, получает реализацию через конструктор
   и допускает её замену. Показания датчиков — учебные константы.

Седьмая работа намеренно не подменена произвольным заданием: известна
только тема, а требуемый принцип или приём программирования не указан.
